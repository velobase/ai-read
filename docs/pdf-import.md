# PDF conversion

PDF import is a separate, reusable pipeline, rather than a special case inside the reader. It produces the same validated `Book → Chapter → Paragraph` format as EPUB/TXT. The ordinary reader, search, notes, translation workflow and reading-pack exporter consume that format unchanged.

## Boundaries

| Layer                 | Web                                                 | iOS                                                        |
| --------------------- | --------------------------------------------------- | ---------------------------------------------------------- |
| Selection and preview | `src/components/pdf/pdf-import-dialog.tsx`          | `apps/mobile/src/components/pdf-import-sheet.tsx`          |
| Extraction            | `src/lib/pdf/parser.ts`, local PDF.js worker/assets | `apps/mobile/src/adapters/pdf.ts`, local Expo module       |
| Native implementation | —                                                   | `apps/mobile/modules/bypage-pdf/ios/ByPagePdfModule.swift` |
| Common conversion     | `packages/reading-core/src/pdf-document.ts`         | Same package                                               |
| Storage               | Existing IndexedDB book storage                     | Existing SQLite book storage                               |

The common converter accepts numbered pages and text blocks. It validates page numbers, normalizes whitespace, splits oversized blocks and emits stable paragraph IDs. `Chapter.sourcePage` retains the original PDF page number even when selected ranges or empty pages create gaps. `Book.sourceFormat` and `sourcePages` describe the source. A PDF page remains one stored `Chapter` segment for compatibility, and may reflow into several screen pages; reading navigation can separately follow the document's logical chapters.

Book IDs include a file digest, extraction engine/version, selected range and (on iOS) OCR mode. Different engines may segment text differently; these IDs prevent incorrect reuse of notes or translations against different paragraph boundaries. Moving a parsed reading pack between platforms retains its existing IDs and text.

New imports use `pdfjs-v2` on the web and `pdfkit-v3` on iOS. Existing parsed books are not rewritten when an extraction rule changes. The web version no longer treats a subscript or superscript font-size change as a paragraph boundary. It excludes a page number only when the page is unrotated, the number matches the physical page index, and it is an isolated short number in the bottom-right margin. Other numbers remain. The native version joins a detached numeric list marker to its nearby text only when there is a unique match on the same visual line; it preserves the text's existing reading order rather than sorting the entire page.

## Chapter navigation

The contents menu can expose a document's logical chapters while retaining the physical-page list. `inferPdfToc` conservatively recognizes an explicit English `Chapter N` paragraph followed by a separate short, uppercase title. It requires at least three consecutive chapter numbers in increasing source-page order. Duplicate or skipped chapter numbers, missing page references or ambiguous titles fall back to the original-page list. This is a limited text-based inference rule, not general PDF outline recognition or AI analysis.

New imports save a validated optional `Book.toc`. Existing books without one derive their menu at runtime from their stored paragraphs, including legacy PDF IDs without `sourceFormat`; no reimport or model request is required. The physical `Chapter` objects, chapter titles, paragraph text, paragraph IDs and `sourcePage` values remain unchanged. Notes, translation hashes and saved reading positions continue to reference those same text anchors.

When a structured directory is available, both readers and book-detail pages offer **Chapters / Original pages**. Chapter entries show their source page and jump to the existing heading paragraph. The active chapter remains selected as reading advances through later physical pages. The original-page list keeps front matter and other pages without detected chapter headings reachable. Without a reliable structure, the menu remains the list of imported pages; skipped empty pages are still available only in the retained original PDF viewer.

The shared `readingChapterNavigation` also supplies the reader's current title and explicit previous/next chapter controls in the progress panel. Web exposes the panel in More as well as the mobile toolbar. A jump uses the target paragraph, so two chapters beginning on the same original page stay distinct. Front matter before the first reliable chapter remains reachable page by page, including text before a chapter that begins partway through that same page. Invalid paragraph anchors and unusable directories fall back conservatively to physical pages. The immutable-book navigation index is cached; subsequent reading-position lookups use a map and binary search.

Ordinary page-turn edges and the continuation at the bottom of a physical page still traverse adjacent imported pages. They do not skip to the next logical chapter. PDF-specific labels distinguish these original-page actions, and the reader no longer inserts a large synthetic page title into the body; source-page markers and actual extracted headings remain visible. These are presentation/navigation changes only, with no migration of text, IDs, progress or translation caches. Web translation preparation still operates on stored physical-page segments and now labels those work units as PDF pages; native chapter preparation retains its existing logical paragraph scope.

The conversion does not preserve PDF links, footnote relationships, annotations or a general outline hierarchy in the parsed book. Detecting chapter headings does not reconstruct those structures. The local original viewer's document-local navigation is separate from the reflowed reading format.

### AI chapter scope

Web and native companion retrieval and conversation-history filtering share `readingScopeParagraphs`. For PDFs, a reliable top-level directory entry defines a half-open interval of actual paragraphs, ending at the next chapter anchor. Two chapter headings on the same physical page therefore remain separate. Nested section headings do not shorten their enclosing chapter. Front matter, missing anchors and unreliable directories fall back to the current physical-page segment, clipped at known local boundaries; they do not silently authorize the entire book. EPUB and text books retain their spine chapter scope.

Source ordering follows the stored paragraph sequence, never numeric parsing of opaque IDs such as `pdf-30.1`. Web retains its 46,000-character accounting and 400-passage retrieval limits; native uses 16,000 source characters and 200 passages with explicit full/partial coverage. This changes evidence selection only: physical chapters, source text, paragraph IDs and translation hashes stay unchanged. Native same-page chapter scope and persistent citations were checked on the Keynes sample; see [native assistant](native-assistant.md).

## Import flow

1. Pick a PDF from the device. Maximum file size is 30 MB; maximum source length is 1,000 pages.
2. If encrypted, enter the password. It stays in memory for extraction and is not written to the book or diagnostics.
3. Choose a page range. The UI explains that text and page references are retained, while complex page layout is not.
4. Parse locally, with page progress, pause/continue and cancellation. Extracted text is limited to 20 × 1,024 × 1,024 UTF-16 code units (`text.length` on web, `utf16.count` on iOS); this is a text-length limit, not a byte or memory-size guarantee.
5. Review the extracted text, skipped page numbers and title. Nothing is added to the library before confirmation.
6. Save through the host's normal book-import operation. Native temporary picker files are discarded when the sheet finishes.

### Inspect a completed conversion

Before saving, Web and iOS can browse every physical page represented by the completed report. Enter an original PDF page number or use Previous/Next within the current filter. A number must identify an actually parsed page; unparsed ranges are not fabricated as empty pages. **All pages**, **No extracted text** and, when present, **OCR pages** expose the report's status. A page without extracted text remains selectable and explains that it will be omitted from the reflowed book; this is not a claim that the original page is visually blank.

Each page shows its extraction method and paragraph count. The preview mounts at most four complete paragraphs at a time, with controls to reach every remaining paragraph and a bounded text viewport. It no longer truncates inspection to the first three nonempty pages or the beginning of their text. Changing page or filter resets the paragraph batch; entering a valid physical page switches back to All pages. A fresh conversion resets preview state even if its book ID is unchanged.

`packages/reading-core/src/pdf-import-preview.ts` indexes existing `Chapter.sourcePage`, `emptyPages` and `ocrPages` without copying or changing paragraph text, identifiers or the Book. Invalid or contradictory report metadata cannot enable confirmation. Preview navigation never extracts the PDF again, prepares a translation or writes a reading position. The preview shows reflowed extraction, not a source-page image; original layout remains available in the retained original viewer after import. OCR attempted on a page but yielding no text is reported as no extracted text, not a successful OCR page.

### Pause and recover within an import

Pause retains completed pages in memory for the currently open file and selected range. Continue starts at the first unfinished physical page, including after a page-level failure. Completed pages without extracted text are retained too; an interrupted or failed page is never committed as an empty page. A recoverable failure identifies its physical page and completed count. Reaching the text limit requires choosing a smaller range instead of repeatedly retrying the same limit. A completed document without recoverable text returns to range selection. No partially parsed Book can be saved.

The UI waits in Pausing until the active run settles before offering Continue. Closing or choosing a different range permanently releases that checkpoint; it does not survive app/browser restart. Closing invalidates late callbacks immediately and waits for extraction and metadata inspection before removing a native temporary preview file. The pending Files inbox item remains available after cancellation.

Web keeps its PDF.js document and completed numbered pages for the exact range. Native hosts advertising `resumableExtractionVersion: 1` retain one fixed file/password/range/OCR session with its completed pages and cumulative text budget. The adapter serializes explicit closing operations before a new run. Vision requests can be cancelled; PDFKit synchronous text extraction or page drawing must return before the current uncommitted page is discarded. The new native capability requires a host rebuild. Older hosts retain full-range parsing, expose no Pause control, and do not claim that a failed parse has resumable progress.

The shared `pdf-parse-state.ts` contract carries only fixed interruption codes, completed/total counts and an optional physical page. Neither engine exposes raw PDF errors through these recovery messages. Checkpoints change scheduling, not extraction rules, paragraph boundaries, engine versions or Book IDs.

Both engines reject PDFs whose copying permissions prohibit text extraction. They do not remove DRM or bypass restrictions. Web extraction uses PDF.js text content; it does not execute embedded PDF scripts. The worker, CMaps, fonts and WASM are served locally from `public/pdfjs`, prepared by `scripts/prepare-pdf.mjs` during install/build. No CDN is needed.

## Scans and fidelity

On iOS, **Recognize scanned pages** uses Apple Vision OCR only on pages without a text layer. The original PDF page is rendered locally at bounded resolution. Results are marked as OCR in the preview, and should be reviewed before saving. The web preview has no OCR engine; pages without text are reported and skipped. A PDF with no recoverable text is rejected with a clear explanation.

Text conversion can still flatten multi-column order, complex tables, mathematical notation, decorative fonts and image captions. OCR is not guaranteed to recover every word. The reader also offers **PDF original** in its More menu: web renders a local PDF.js canvas, and iOS uses PDFKit. This retains the source page's graphics and mathematical layout alongside reflowed text. The viewer starts at the current physical page; **Read this page's text** returns to that page's existing chapter, when one was imported. It does not perform another conversion or change text anchors.

New PDF imports retain the original locally. Existing parsed books can associate the same original file; SHA-256 must match the book's source fingerprint. Web stores the Blob separately in the current account/guest IndexedDB. iOS stores it in application support with file protection and excludes it from device backup. Raw PDFs are not included in account sync or reading packs. Removing a book cleans up its local original. Keep the original PDF separately for other devices. Passwords stay in the mounted viewer's memory. Web renders page graphics without a PDF action/link layer; native navigation permits document-local destinations and ignores external URL, remote-document and print actions.

Import and original-page viewing do not call an AI model, upload the PDF, generate translations or make network requests to a document-conversion service. A later explicit AI action follows the reader's existing model-connection behavior.

### Native library-scoped originals

The native adapter's `retainPdfOriginal`, `getPdfOriginal` and `removePdfOriginal` require an immutable `LibraryHandle` as their first argument. Device originals keep the existing `Application Support/pdf-originals/<book-ID-digest>.pdf` path. Account originals use a separate `account-<64-hex-scope-digest>` subdirectory, derived from canonical origin and stable user ID by the library-scope adapter. The book ID and source-file fingerprint are unchanged; an account association never falls back to a device original with the same book ID.

The updated PDF module advertises `scopedOriginalVersion: 1` and provides explicit scoped retain/get/remove methods. It accepts only `device` or the exact account-scope form, rejects symbolic-link aliases in destination paths, and checks that an original-view URI is a directly contained hashed PDF in the requested scope. Scope changes also invalidate pending native view loads. The legacy methods remain fixed to the device directory. On an older native host, device operations continue through those methods while account-original operations fail as unavailable; they do not silently use the device directory. The scoped methods and view property require a native rebuild.

Import previews carry the original `LibraryLease`. Picker/parse completion, confirmation and export check that lease after asynchronous work; the PDF save callback receives the same frozen destination. Retain, book save and any failed-save cleanup all address that destination's handle. Cleanup removes a newly retained original only when the book is confirmed absent from that same library, preserving sources whose book save succeeded before a later refresh failed. Picker and preview cache copies remain separate from the caller's source file. The Files inbox remains device-level staging, with its destination selected when preparing an import.

These are storage and lifecycle boundaries, not proof of an enabled account-library workflow. The App's active device library remains compatible; account grant/switching, outbox and cross-device original-file transfer are separate work. This increment received static review, Swift syntax parsing and a successful full native build. Account switching and account-original isolation have not been manually exercised; device-path runtime observations are recorded separately when completed.

### Original-page controls

Both original viewers accept a one-based physical PDF page number. Only decimal integers within the actual document's page count are accepted; printed page labels and inferred chapter numbers are separate. Web restores the confirmed input after invalid entry. Native displays an inline correction and offers previous/next-page buttons plus an optional, horizontally scrolling PDFKit thumbnail strip. The strip uses the already-open document and is detached when hidden; it does not pre-render an application-owned image array for every page.

Native commands carry separate document and navigation identities. A jump is acknowledged from PDFKit's actual current page, including a repeated request for the same page after manual browsing. Late callbacks from another document or command cannot enable a return to stale text. **Read this page's text** stays disabled until confirmation, and on Web until the displayed canvas belongs to that document and page. A physical page omitted during text import remains viewable but cannot be reflowed without imported text. Browsing the original alone does not move the stored reflowed position; explicit return does, while returning to the same source page preserves its existing text anchor.

These native controls require an updated app host advertising navigation support. Older hosts retain swipe browsing and explain that page entry and thumbnails require an update. Web does not include the native thumbnail strip. Opening the original still uses only the retained local PDF; no translation or conversion is triggered.

### Find in the original PDF

Both viewers search the retained local PDF's text layer without changing the reflowed book. Queries are literal, case insensitive, at most 160 UTF-16 units, with flexible whitespace for phrases split over lines. There is no automatic first-result jump: Next or Previous chooses a match. Manual page entry and page buttons clear the active match while retaining results. Search queries and text are not stored or sent to diagnostics, translation services or OCR.

Search is sequential, cancellable and limited to 2,000 matches; one additional match proves truncation. A complete scan with no searchable text has a separate explanation. Both engines bound cumulative extracted text at 20 Mi UTF-16 units. Native additionally allows 1 Mi per page; Web allows 2 Mi and 50,000 text items per page. These are work budgets, not guarantees about PDF engine memory consumption. Web can stop and keep partial results; native Clear or closing Find cancels the query and discards its results.

Web preserves original TextItem UTF-16 ranges and measures a temporary PDF.js TextLayer with DOM ranges at the actual canvas viewport. Only the selected match's rectangles survive, and document/query/attempt/page/zoom identities reject stale layouts. Native uses a separate PDFDocument on a serial background queue; search results send physical page numbers while verified ranges remain native. A new navigation identity selects a PDFSelection and reveals its surroundings using PDFKit coordinate conversions. Read-page navigation uses the confirmed actual page, never a PDF text offset. Native search requires a host advertising `searchVersion: 1`; older hosts keep the existing original-page viewer. The selected-hit evidence extension below adds an independently verified reflowed location.

### Read a search hit in the reflowed text

**Read this page's text** can also locate the selected original-file search occurrence. The shared `resolvePdfTextEvidence` converter matches its complete text and adjacent context against only the already imported paragraphs from that physical page. It normalizes Unicode compatibility forms, whitespace and soft hyphens while mapping back to the original paragraph's UTF-16 boundaries. It does not use a PDF engine offset as a reading offset or change stored text, paragraph IDs or annotations. A same-page selected hit can therefore move from the page start to its corresponding reading screen, with a return point for the earlier position.

Evidence retains the complete match (at most 640 UTF-16 units) and up to 80 units on each side. It is never shortened to impersonate a longer match. All supplied context must match uniquely; empty context means the actual original-page boundary. Missing or ambiguous text, removed headers, reordered columns, partial composed characters and unsupported normalization boundaries keep the existing page-level behavior. Cross-paragraph matches locate their first matched paragraph. Processing is bounded to 1 Mi source units, 2 Mi normalized units, 4,096 paragraphs and 1,024 candidates per page; the returned real paragraph quote is at most 280 units. There is no fuzzy/OCR correction.

Web retains this small evidence beside its in-memory search hits and checks the selected document, query, search attempt and actual rendered page before passing it to the reader. Native hosts with `searchEvidenceVersion: 1` send only the explicitly selected hit's evidence in the confirmed page event, with document, navigation, search and index identities. Leaving the hit's physical page invalidates that evidence, even if the user scrolls back; selecting the hit again establishes new evidence. Query changes, manual page entry, dismissal and library blocking also invalidate it. Older native hosts continue page-level navigation. Evidence is not persisted, exported, logged or sent to a model.

## Diagnostics and validation

The web records a bounded `pdf_parse` operation with success, error or cancelled status; native diagnostics use `pdf.parse` with the same outcomes. Native pause and cancellation are classified as cancelled. Each run includes interpretation of the extraction result, so paused/failed native envelopes are not recorded as successful conversions. Both record timing without PDF text, passwords, file names or document metadata. Native events stay on device in memory unless exported by the user.

A four-page original fixture was manually checked in the browser and iOS Simulator on 2026-10-23. It includes an English text page, a Chinese text page, one image-only page and one blank page. Web imported the two text pages and reported the other two. iOS with OCR imported three pages, reported the blank page and displayed the OCR text in the normal reader. See [mobile verification](mobile-verification.md) for screenshots and limits of verification.

The same day, Keynes's _The General Theory of Employment, Interest, and Money_ was checked as a real 190-page text-layer PDF. The web `pdfjs-v2` flow parsed all 190 pages, saved the book, and opened original page 100 through the reader's contents menu. That page produced seven text blocks after the paragraph fix, instead of the previous 26 fragments. Its fraction remained linearized text; mathematical page layout was not restored. The source PDF has no outline or linked contents. Its initial menu was page-based; the later chapter-heading inference described above adds a structured view without changing those parsed pages.

A subsequent manual check opened this PDF's original page 100 in the web viewer, showing the fraction and subscripts in their original layout. Web zoom and the page-101 return to reflowed text were checked. The iOS Simulator rejected a different PDF during association, accepted the matching source, reopened it from local storage, and returned from original page 101 to text chapter 101. The full-screen header's safe-area overlap was corrected and visually rechecked. This is targeted verification, not coverage of all PDF variants, password behavior or pinch gestures.

After rebuilding the native app, the iOS `pdfkit-v3` flow also parsed all 190 pages again. The page-2 preview showed list numbers joined to their corresponding titles, and confirmation saved the new parsed book to the local library. This establishes full-file parsing, corrected preview and storage; it does not establish fidelity for every page. The real-book files, extracted text and private screenshots were kept outside this repository.
