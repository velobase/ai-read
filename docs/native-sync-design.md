# Native account-library sync: implementation boundary

The native App now connects the explicit v2 library authorization, isolated account-library selection, and synchronization of books, progress, notes and bookmarks. These paths are implemented in source; real account authorization, a complete sync round trip, and switching between multiple real accounts have not yet been verified. The existing device library remains separate and is never uploaded merely by signing in or granting access.

## Authorization and storage

Existing mobile sessions retain `account_ai`; they are not upgraded automatically. The account screen has a separate “Authorize and open account library” action using `/mobile/library/authorize` and `/api/mobile/v2/auth/authorize`. Browser confirmation grants the fixed `account_ai` plus `library_sync` profile. The native host must advertise its library-auth capability, and `/api/mobile/v2/config` must support the four negotiated entities. The v1 API continues to report `nativeAccountSync: false` for older clients. See the [v2 protocol](native-sync-protocol.md) for endpoint and permission details.

`library-scope.ts` binds each account database to the canonical server origin and stable user ID, hashed into an opaque filename and attachment scope. Session IDs, email addresses and tokens do not identify storage. The existing `bypage-v1.db` remains the device library; it is neither renamed nor migrated. Account databases are not seeded with the device sample or populated from device books. Creating a handle opens no database by itself.

The App starts in the device library. Users explicitly open an authorized account library or return to the device library. Reopening the same origin/user addresses the same account cache. Signing out or changing account identity does not delete either cache. Device preferences remain device-level, with a serialized write queue across library remounts.

## Library lifetimes

`LibraryHost` prepares the target database, blocks interaction, asks the reader to capture and flush its position, and waits for the old database's transaction barrier before revoking the old lease and mounting the new scope/epoch tree. An account destination is checked against the current origin, stable user ID and permission before activation. Account content is blocked while identity is unavailable or changing; the user can return to the device library if a switch fails.

All library business functions require an immutable handle. Readers retain the handle that loaded their book, so a terminal position write can only finish in its original database. Search, assistant work, imports, PDF extraction and exports cancel or fence delayed results with their captured lease. Translation jobs and caches, collection subscriptions, covers and image paths also include library identity. Account-request revisions remain a separate network fence. Already presented system share windows cannot be recalled by a lease change.

PDF originals and EPUB image caches use separate account namespaces while preserving existing device paths. The native PDF viewer checks the exact scoped original directory. Older native hosts support device originals but refuse account attachments. Raw PDF originals have no sync transport field.

## Atomic local mutations and synchronization

Only account databases maintain `library_sync_state`. Adding or supplementing a book, changing its source language or finished state, saving progress, editing notes or bookmarks, importing a reading pack, and changing group membership stage their outbox mutation in the same SQLite transaction as the local change. Subscribers are notified after a successful commit. Device writes do not create outbox entries.

The outbox stores the server version and shadow, plus the pending mutation ID, base version, deletion flag and data. A successful acknowledgement clears only the matching mutation; a later local edit remains pending and is rebased. Late delete acknowledgements cannot discard a newer explicit reimport. Book shelf fields unknown to the native UI, such as Web pin/hidden state, survive local edits. Concurrent book changes use a three-way field comparison; local fields do not overwrite unrelated Web changes. Group membership travels in each book's shelf state. Empty groups have no independent sync entity and remain local.

First uploads, compatible media additions and explicit resurrection of a tombstoned book retain full content. Routine updates to an acknowledged book use metadata and shelf state; SQL projects those fields without transferring the entire book body to JavaScript. An outstanding full upload is not downgraded by a subsequent position update. Ordinary metadata acknowledgements avoid downloading full content again unless a conflict or media revision requires it.

The account transport uses v2 mobile Bearer credentials, the exact account-identity header, CAS versions and idempotent mutation IDs. It does not fall back to cookies or device credentials. The foreground sync hook schedules work for the available library screen, after committed changes and on returning to the foreground; it does not replace an open reader's content snapshot or promise background synchronization. The account panel exposes pending/rejected status and explicit retry. Counts are hydrated from local SQL before/after a pass and after local commits; unavailable counts are never reported as zero. Fixed error categories distinguish authorization, permission, connection, timeout, service, protocol, rejection and storage failures. Foreground network failures use 5-second exponential backoff capped at 5 minutes. Authorization, protocol and storage failures pause automatic retries until a foreground, authorization or manual retry. Rejected mutations remain local and are not automatically resubmitted; a new local mutation can send other eligible work without starting a retry loop.

A newly downloaded or replaced book and its initial progress are applied atomically. Original book and paragraph IDs remain authoritative: PDFKit and PDF.js intentionally produce different parsed-book identities, and matching titles or source-file hashes do not merge their annotations.

## Recovery and explicit copying

Before a local account-book deletion, remote deletion or conflicting overwrite, the storage layer preserves the relevant complete local book snapshot. This includes progress, notes, bookmarks, saved translations, translation drafts, AI history, group membership and sync state. Recovery records have no cascading foreign key, and account PDF originals are retained. A remote parent deletion stops pending child records from being retried against that deleted parent.

The recovery panel can restore directly into an independent device copy, or export a reading pack or complete recovery archive. The reading pack contains supported book, note, bookmark, progress, saved-translation and group data. The complete archive additionally retains private history, drafts and outbox records. Both formats have explicit import previews; complete archives always restore into the device library, even when selected from an account screen. The JSON import/share limit is 50 MiB. Original PDF bytes are not embedded in either export.

Recovery uses a reserved fresh book ID and an atomic transaction for all restored rows plus its completion marker. Paragraph IDs, media references, translation keys and annotation anchors stay unchanged; only book ownership is mapped to the new ID. Repeated imports of the same validated archive reuse the completed copy without overwriting later edits. If the user deleted that copy, retry reports this instead of silently resurrecting it; the original recovery remains exportable. History/drafts keep their service/account/context partition. Incompatible private rows are counted and skipped, while invalid core reading data rejects the archive. Recovery never imports credentials, preferences or outbox operations.

Internal account recovery may copy a retained PDF original after checking its source hash. Missing originals do not prevent restoring readable text and produce an explicit result. Failure compensation only removes a newly created, uncommitted target attachment. External JSON is data only: its library identity is never used to open an account directory or read account attachments. A completed recovery does not subsequently backfill a previously missing PDF original. EPUB assets remain embedded under their original references.

Copying from the device library is a separate action: select one book and confirm its destination account. The additive copy retains the device original and preserves existing same-ID account records. The book, progress, notes, bookmarks and membership can then synchronize through the four allowed entities. Saved translations are copied only into the local account cache. PDF original files, AI history and translation drafts are not copied by this action. A title match never substitutes for compatible book content.

## Remaining boundaries and verification

Independent saved-translation, AI-history and preference synchronization are outside this grant. They need separate versioned contracts and new consent. Native portable translations hold one saved version per language; arbitrary Web edition keys must not be relabelled as that cache. The four-entity grant still discloses that deleting an account book cascades its associated cloud records, including saved translations and conversations.

Real account authorization, account-to-Web round trips, offline retry/recovery behavior and multi-account switching remain runtime verification work. Existing device data is kept in its original database, and no real account-library transfer has been established by the current verification record. Source review, type checking or a successful build must not be presented as evidence of those runtime behaviors. The earlier permission migration ran against the confirmed local database with empty account tables; it did not exercise a real legacy token. Build and simulator observations are recorded separately in [mobile verification](mobile-verification.md). No automated tests were added or run for this increment.
